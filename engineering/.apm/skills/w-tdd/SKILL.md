# 测试驱动开发

TDD 就是红 → 绿这个循环。本文说明如何让这个循环产出值得保留的测试——什么算好测试、测试置于何处、哪些写法属于反模式、循环中应遵守什么规则。各节在每一轮循环中均适用，须在开始之前与进行过程中查阅，而非事后补读。

探索代码库时，读 `GLOSSARY.md`（如果有），让测试名和接口用词与项目的领域语言一致，并遵守你正触及区域的 ADR。

## 什么是好测试

测试验证的是**行为**，通过**公开接口**，而不是实现细节。代码可以整体重写，测试不该跟着变。好测试读起来像一份规格：`用户可以拿有效购物车下单` 明确告诉你存在什么能力，而且它在重构后依然成立，因为它不关心内部结构。

例子见 [tests.md](tests.md)，mock 的写法见 [mocking.md](mocking.md)。

## 接缝：测试写在哪

**接缝（seam）** 是你测试所处的公开边界：在那个接口上你能观察行为，而不用把手伸进去。测试住在接缝上，绝不针对内部实现。

**只在事先约定的接缝上写测试。** 动手写任何测试之前，先写下要测的接缝，并与用户确认。没有确认过的接缝，不写测试。你不可能测遍一切，所以事先约定接缝，正是让测试精力落在关键路径和复杂逻辑上、而不是每个边界情况上的办法。

问：「公开接口是什么，我们要测哪些接缝？」给每个提议的接缝配一句话，说明它能抓到什么、漏掉什么。

当接口本身的形状还有疑问时（模块多深、接缝该在哪、接口该暴露什么），调用 Skill 工具执行 `w-codebase-design` 获取术语。module、interface、depth、seam、adapter、leverage、locality 这些词的统一定义都在那里；只取词即可，不必真的跑一场会话。

## 反模式

- **与实现耦合**：mock 内部协作者、测私有方法、或通过侧信道验证（直接查数据库而不是走接口）。识别信号：行为没变，但一重构测试就挂。
- **同义反复**：断言用和代码一样的方式重算期望值（`expect(add(a, b)).toBe(a + b)`、手工照同样方式导出的快照、把自己的常量断言成自己），于是它按构造必然通过，永远不可能和代码不一致。期望值必须来自独立的单一真相来源：一个已知正确的字面量、一个手算的例子、或规格。
- **横向切片**：先把所有测试写完，再写所有实现。批量测试验证的是*想象的*行为：你测的是东西的*形状*而不是面向用户的行为，测试对真实变化变得不敏感，而且你在还没理解实现之前就把测试结构定死了。改成**垂直切片**：一个测试 → 一个实现 → 再来下一个。每个测试只向前推进一小步，用上一轮得到的发现决定下一步怎么写。

## 循环规则

- **先红后绿。** 先写失败的测试，再只写够让它通过的代码。不要提前为未来的测试做准备，也不要加投机性功能。
- **一次一个切片。** 每轮一个接缝、一个测试、一个最小实现。
- **重构不属于这个循环。** 它属于评审阶段（见 `w-code-review` 技能），不属于红 → 绿的实现循环。
