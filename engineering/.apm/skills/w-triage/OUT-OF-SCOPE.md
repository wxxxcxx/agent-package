# 不在范围内知识库

仓库中的 `.out-of-scope/` 目录持久记录被否决的功能请求，用途有二：

1. **组织记忆**：功能为何被否决，issue 关闭后理由不至于散失
2. **去重**：新的 issue 与既往否决相符时，技能可以呈现旧决策，而不必重新争辩一遍

## 目录结构

```
.out-of-scope/
├── dark-mode.md
├── plugin-system.md
└── graphql-api.md
```

一个**概念**一个文件，而非一个 issue 一个文件。请求同一件事的多个 issue 归入同一文件。

## 文件格式

文件宜写得从容易读，更接近一篇简短的设计文档，而不是数据库条目。用段落、代码样例与实例把理由讲清楚，使初次读到的维护者也能看懂。

```markdown
# 深色模式

本项目不支持深色模式，也不提供面向用户的自定义主题。

## 为什么不在范围内

渲染管线假定只有一套色板，定义在 `ThemeConfig` 中。要支持多主题，需要：

- 一个包裹整棵组件树的主题上下文提供者
- 每个组件都按主题解析样式
- 一层持久化，保存用户的主题偏好

这是相当规模的架构改动，与本项目专注于内容创作的定位不符。主题属于下游消费者
的关切，由它们嵌入或再分发输出时自行处理。

```ts
// 当前 ThemeConfig 接口并非为运行时切换而设计：
interface ThemeConfig {
  colors: ColorPalette; // 单一色板，构建时解析
  fonts: FontStack;
}
```

## 既往请求

- #42 —— 「支持深色模式」
- #87 —— 「无障碍夜间主题」
- #134 —— 「深色主题选项」
```

### 文件命名

概念名用简短、可读的 kebab-case：`dark-mode.md`、`plugin-system.md`、`graphql-api.md`。名字要足够明确，使浏览该目录的人不必打开文件就知道被否决的是什么。

### 如何写理由

理由要有实质——不是「我们不想要」，而是为什么不想要。好的理由通常指向：

- 项目范围或理念（「本项目专注 X，主题属于下游关切」）
- 技术约束（「支持它需要 Y，与本项目的 Z 架构冲突」）
- 取舍决策（「我们选择 A 而非 B，因为……」）

理由应耐久。避免写入临时状况（「最近太忙」），那不是真正的否决，只是推迟。

## 何时查 `.out-of-scope/`

分诊的第 1 步（收集上下文）中，读取 `.out-of-scope/` 下的全部文件。评估新 issue 时：

- 检查请求是否与既有条目指向同一概念
- 匹配依据是概念相似，而非关键词——「夜间主题」应命中 `dark-mode.md`
- 命中时向维护者呈现：「这与 `.out-of-scope/dark-mode.md` 相似——我们此前否决过，理由是……你还持同样看法吗？」

维护者可能：

- **确认**：新 issue 追加到既有文件的「既往请求」列表，然后关闭
- **重新考虑**：删除或更新该文件，issue 走正常分诊
- **不同意**：两者相关但不同，走正常分诊

## 何时写 `.out-of-scope/`

只在**功能请求**（而非 bug）被否决为 `wontfix` 时。功能类 PR 同样适用：被否决的 PR 也要记录，以免同样的请求换个形式再来一次。

若某事项是以 `wontfix` 关闭的**已实现**功能，**不要**写入此处。那是已建成的功能，不是被否决的请求；记进去会用假否决污染去重检查。正确做法是在关闭评论中指出该功能所在位置。

流程：

1. 维护者判定某功能请求不在范围内
2. 检查是否已有匹配的 `.out-of-scope/` 文件
3. 有：把新 issue 追加到「既往请求」列表
4. 无：新建文件，写入概念名、决策、理由与第一条既往请求
5. 在 issue 上评论说明决策，并提及该 `.out-of-scope/` 文件
6. 打 `wontfix` 标签关闭 issue

## 更新与删除

维护者改变主意时：

- 删除对应的 `.out-of-scope/` 文件
- 技能无需重开旧 issue，它们只是历史记录
- 触发这次重新考虑的新 issue 走正常分诊
