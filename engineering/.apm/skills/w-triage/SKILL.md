# 分诊

把项目 issue tracker 上的 issue 推进一组分诊角色构成的小型状态机。

若本仓库把外部 pull request 也当作请求入口（见 issue-tracker 配置），则 PR 同样纳入分诊范围：**PR 是附带代码的 issue**，角色、状态、状态机完全一致，下文标注「针对 PR」处为差异项。裸写 `#42` 时，按 tracker 配置判断它是 issue 还是 PR。

分诊期间向 issue tracker 发布的每条评论或 issue，**必须**以下述声明开头：

```
> *This was generated by AI during triage.*
```

## 参考文档

- [AGENT-BRIEF.md](AGENT-BRIEF.md)：如何撰写可长期留存的 agent 简报
- [OUT-OF-SCOPE.md](OUT-OF-SCOPE.md)：`.out-of-scope/` 知识库的工作方式

## 角色

两个**类别**角色：

- `bug`：功能损坏
- `enhancement`：新功能或改进

五个**状态**角色：

- `needs-triage`：待维护者评估
- `needs-info`：等待报告者补充信息
- `ready-for-agent`：已完整描述，可由 AFK 运行的 agent 接手
- `ready-for-human`：需人工实现
- `wontfix`：不予处理

针对 PR，同样的状态对应其附带的代码：`ready-for-agent` 表示已附简报、应由 agent 在 diff 上推进下一步；`ready-for-human` 表示可由人工合并。

每个完成分诊的 issue 应恰好携带一个类别角色与一个状态角色。若状态角色互相冲突，先标记出来并询问维护者，再做其他任何操作。

以上为角色的规范名称，issue tracker 中实际使用的标签字符串可能不同。二者的映射应已提供；若未提供，提示用户先运行 `/w-setup-project`。

状态流转：未打标签的 issue 通常先进入 `needs-triage`，由此转向 `needs-info`、`ready-for-agent`、`ready-for-human` 或 `wontfix`；`needs-info` 在报告者回复后回到 `needs-triage`。维护者可随时覆盖，遇到不寻常的流转应先标记并询问，再继续。

## 调用方式

维护者用自然语言描述需求并调用 `/w-triage`，据此理解意图并执行。示例：

- 「看看有哪些需要我处理」
- 「看下 #42」（issue 或 PR）
- 「把 #42 移到 ready-for-agent」
- 「有哪些已经可以交给 agent？」

## 展示待处理事项

查询 issue tracker，按最早优先分三组呈现：

1. **未打标签**：从未分诊。
2. **`needs-triage`**：评估进行中。
3. **上一条分诊记录之后报告者有新动态的 `needs-info`**：需要重新评估。

PR 在范围内时，将外部 PR 一并纳入上述三组，并在每行标注 `[PR]` 或 `[issue]`。发现环节只呈现**外部** PR（外部与否由 tracker 配置定义），协作者正在进行的 PR 不属于分诊工作。该过滤仅作用于发现环节：被明确点名的 PR，无论作者是谁都要分诊。

展示各项计数与一行摘要，由维护者挑选。

## 分诊指定的 issue 或 PR

1. **收集上下文。** 通读 issue 或 PR 全文（正文、评论、标签、作者、日期；PR 另需阅读 diff）。解析既往分诊记录，避免重复提问已解决的问题。按项目领域术语表探索代码库，并遵守该区域的 ADR。对代码库做两项检查：(a) **重复实现**：按领域概念（而非请求中的字面措辞）搜索既有实现，并报告搜索位置；若已存在，属于已实现的 `wontfix`（见第 5 步）。(b) **既往否决**：阅读 `.out-of-scope/*.md`，找出与本请求相似的条目。

2. **给出建议。** 向维护者说明建议的类别与状态及理由，并附一段与请求相关的代码库摘要（含是否已实现）。等待指示。

3. **验证所述。** 在拷问之前先确认其成立。对 bug，按报告者的步骤复现；对 PR，确认 diff 确实做到了它声称的事——取回分支，运行相关测试或命令。报告结果：已确认（附代码路径）、验证失败，或细节不足（属于明确的 `needs-info` 信号）。验证通过的结论能显著增强 agent 简报。

4. **拷问（按需）。** 若请求需要补全，调用 Skill 工具两次，分别执行「grilling」与「domain-modeling」，按轮次提问将其梳理成形，同时校准领域术语，并在决策落定时同步更新 `GLOSSARY.md` 与 ADR。

5. **落实结论：**
   - `ready-for-agent`：发布 agent 简报评论（见 [AGENT-BRIEF.md](AGENT-BRIEF.md)）。
   - `ready-for-human`：结构同 agent 简报，但需说明为何不能委派（需判断力、需外部权限、需设计决策、需人工测试）。
   - `needs-info`：发布分诊记录（模板见下）。
   - `wontfix`：关闭 issue，评论内容取决于**原因**：
     - **已实现**：代码库中已存在该变更。指出位置；**不要**写入 `.out-of-scope/`（该知识库只记录被否决的请求，不记录已建成的功能）。
     - **否决（bug）**：礼貌说明后关闭。
     - **否决（enhancement）**：写入 `.out-of-scope/`，在评论中链接该条目后关闭（见 [OUT-OF-SCOPE.md](OUT-OF-SCOPE.md)）。
   - `needs-triage`：直接套用该角色。若已有部分进展，可附一条评论。

## 快速覆盖状态

维护者说「把 #42 移到 ready-for-agent」时，直接采信并套用角色。先复述将执行的操作（角色变更、评论、关闭），再执行，跳过拷问。若在未做拷问的情况下移入 `ready-for-agent`，询问是否需要撰写 agent 简报。

## needs-info 模板

```markdown
## Triage Notes

**目前已经确认的内容：**

- 要点一
- 要点二

**仍需你（@reporter）补充的内容：**

- 问题一
- 问题二
```

拷问过程中确认的全部内容都应归入「目前已经确认的内容」，避免工作成果流失。问题须具体、可执行，不使用「请提供更多信息」这类空话。

## 恢复此前的分诊

若该 issue 或 PR 上已有分诊记录，先阅读，检查报告者是否回答了待答问题，呈现更新后的全貌再继续。已解决的问题不再追问。
