# 代码库设计

设计**深模块**：把大量行为藏在一个小接口之后，放在干净的 seam 上，并通过该接口测试。凡是设计或重构代码的场合，都使用这套语言与这些原则。目标是给调用方以杠杆，给维护者以局部性，给所有人以可测试性。

## 术语

以下术语严格照用，不要换成「组件」「服务」「API」「边界」。用词一致正是这套体系的意义所在。

**模块（Module）**：任何同时具备接口与实现的东西。刻意不限定粒度：可以是一个函数、类、包，也可以是横跨多层的一个切片。*避免*：unit、component、service。

**接口（Interface）**：调用方要正确使用该模块所必须知道的一切。不只包括类型签名，还包括不变量、调用顺序约束、错误模式、必要配置与性能特征。*避免*：API、signature（二者过窄，只覆盖类型层面的表面）。

**实现（Implementation）**：模块内部的代码主体。与**adapter**相区别：某个东西可以是小 adapter 加大实现（例如 Postgres 仓储），也可以是大 adapter 加小实现（例如内存假实现）。讨论的焦点是 seam 时用「adapter」，否则用「实现」。

**深度（Depth）**：接口所提供的杠杆。调用方（或测试）每学习一单位接口，能够驱动多少行为。大量行为藏在小接口之后，称为**深**；接口复杂度逼近实现复杂度，称为**浅**。

**seam**（Michael Feathers）：可以在不修改该处代码的前提下改变其行为的地方，即模块接口所在的位置。seam 设在哪里本身就是一项设计决策，与 seam 之后放什么相互独立。*避免*：boundary（与 DDD 的限界上下文混淆）。

**adapter**：在某个 seam 上满足某个接口的具体实现。它描述**角色**（占据哪个位置），而非实体（内部是什么）。

**杠杆（Leverage）**：调用方从深度中得到的收益。每学习一单位接口换来的能力更多。一份实现，回报给 N 个调用点与 M 个测试。

**局部性（Locality）**：维护者从深度中得到的收益。变更、缺陷、知识与验证集中在一处，而不散落到各个调用方。改一次，处处生效。

## 深与浅

**深模块**＝小接口 + 大量实现：

```
┌─────────────────────┐
│   Small Interface   │  ← 方法少，参数简单
├─────────────────────┤
│                     │
│  Deep Implementation│  ← 复杂逻辑藏在内部
│                     │
└─────────────────────┘
```

**浅模块**＝大接口 + 少量实现（应避免）：

```
┌─────────────────────────────────┐
│       Large Interface           │  ← 方法多，参数复杂
├─────────────────────────────────┤
│  Thin Implementation            │  ← 只是转手
└─────────────────────────────────┘
```

设计接口时自问：

- 方法数量能否减少
- 参数能否简化
- 能否把更多复杂度藏进内部

## 原则

- **深度是接口的属性，不是实现的属性。** 深模块内部完全可以由小的、可 mock、可替换的部件组成，只是这些部件不属于接口。模块除了接口处的**外部 seam**，还可以有**内部 seam**（对实现私有，供自身测试使用）。
- **删除测试。** 设想删除该模块：复杂度随之消失，说明它只是个转手环节；复杂度在 N 个调用方处重新出现，说明它物有所值。
- **接口即测试面。** 调用方与测试穿过同一道 seam。若必须绕过接口才能测试，多半说明模块形状错了。
- **一个 adapter 意味着假想的 seam，两个 adapter 才是真实的 seam。** 除非确实有东西在 seam 两侧变化，否则不要引入 seam。

## 为可测试性而设计

好的接口让测试变得自然：

1. **接受依赖，不要自行创建。**

 ```typescript
   // 可测试
   function processOrder(order, paymentGateway) {}

   // 难以测试
   function processOrder(order) {
     const gateway = new StripeGateway();
   }
   ```

2. **返回结果，不要产生副作用。**

 ```typescript
   // 可测试
   function calculateDiscount(cart): Discount {}

   // 难以测试
   function applyDiscount(cart): void {
     cart.total -= discount;
   }
   ```

3. **缩小表面积。** 方法少则测试少；参数少则测试准备简单。

## 关系

- 一个**模块**恰好拥有一个**接口**（即呈现给调用方与测试的表面）。
- **深度**是**模块**的属性，以**接口**为度量基准。
- **seam**是**模块**的**接口**所在之处。
- **adapter**位于**seam**之上，满足**接口**。
- **深度**为调用方产生**杠杆**，为维护者产生**局部性**。

## 不采用的表述

- **把深度定义为实现行数与接口行数之比**（Ousterhout 的原始说法）：这会奖励往实现里灌水。此处采用「深度即杠杆」。
- **把 interface 理解为 TypeScript 的 `interface` 关键字或类的公开方法**：过于狭窄，此处的接口包含调用方必须知道的一切事实。
- **boundary**：与 DDD 的限界上下文混淆。请说**seam**或**接口**。
