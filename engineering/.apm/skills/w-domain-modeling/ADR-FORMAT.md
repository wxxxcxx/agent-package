# ADR 格式

ADR 存放在 `docs/adr/`，按顺序编号：`0001-slug.md`、`0002-slug.md`，依此类推。

`docs/adr/` 目录按需创建，只在第一条 ADR 需要时建立。

## 模板

```md
# {决策的简短标题}

{1 至 3 句：背景是什么，决定了什么，为什么。}
```

就这些。一条 ADR 可以只是一个段落。它的价值在于记录**做过某个决定**以及**理由**，而不在于把各章节填满。

## 可选章节

只有确实带来价值时才加，多数 ADR 用不上。

- **Status** frontmatter（`proposed | accepted | deprecated | superseded by ADR-NNNN`）：决策被重新审视时有用
- **考虑过的方案**：只有被否决的备选值得留档时才写
- **后果**：只有下游影响不显而易见、需要点明时才写

## 编号

扫描 `docs/adr/`，取现有最大编号加一。

## 何时提议写 ADR

以下三条必须同时成立：

1. **难以逆转**：日后改主意的代价不小
2. **脱离上下文会令人意外**：未来的读者看到代码会追问「当初到底为什么这么写」
3. **确有取舍**：存在真实的备选，且你是基于特定理由选定其一

容易逆转的决策就不用写，你迟早会把它改回去；不令人意外的，没人会追问；没有真实备选的，除了「我们照着显而易见的做法做了」没什么可记。

### 哪些算

- **架构形态。**「我们使用 monorepo。」「写模型采用事件溯源，读模型投影到 Postgres。」
- **上下文之间的集成方式。**「Ordering 与 Billing 通过领域事件通信，不用同步 HTTP。」
- **带来锁定的技术选型。** 数据库、消息总线、认证服务商、部署目标。不是每个库都算，只算那些换掉要花一个季度的。
- **边界与范围决策。**「客户数据归 Customer 上下文所有，其他上下文只按 ID 引用。」明确说「不」与明确说「是」同样有价值。
- **对显而易见路径的有意偏离。**「我们用手写 SQL 而不用 ORM，因为 X。」凡是合理的读者会默认相反做法的地方。这类记录能阻止下一位工程师去「修好」一个刻意为之的设计。
- **代码里看不见的约束。**「因为合规要求，不能用 AWS。」「根据合作方 API 契约，响应时间必须在 200ms 以内。」
- **理由不显然的否决。** 若你考虑过 GraphQL，出于微妙的理由选了 REST，就记下来，否则半年后会有人再提一次 GraphQL。
