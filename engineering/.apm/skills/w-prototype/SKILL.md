# 原型

原型是**用来回答某个问题的一次性代码**。问题决定它的形态。

## 先选分支

判断要回答的是哪个问题：依据用户的提示、周围的代码，或用户在场时直接询问：

- **「这套逻辑／状态模型站得住吗？」** → [LOGIC.md](LOGIC.md)。做一个可分享的单个 HTML 文件（自由操作按钮，加上分标签的引导式逐项演示），把状态机推进到纸面上难以推理的情形，并让非开发者也能操作。
- **「界面该长什么样？」** → [UI.md](UI.md)。在同一条路由上生成若干个风格迥异的界面变体，用 URL 查询参数与悬浮底栏切换。

两个分支产出物差别极大，判错分支会浪费整个原型。若问题确实含糊且联系不上用户，按周围代码选择更贴近的分支（后端模块→逻辑；页面或组件→界面），并在原型顶部写明这一假设。

## 两个分支共同遵守的规则

1. **从第一天起就是一次性的，并且明确标注。** 原型代码放在将来实际使用它的位置附近（紧邻被原型的模块或页面），使上下文一目了然；命名要让随便看一眼的人就知道这是原型而非生产代码。一次性的界面路由沿用项目既有的路由约定，不要另建顶层结构。
2. **启动方式要极简。** 界面原型由项目任务运行器的一条命令启动：`pnpm <name>`、`python <path>`、`bun <path>` 等。逻辑演示则是一个双击即可打开的 HTML 文件。两者都不需要思考如何启动。
3. **默认不做持久化。** 状态放在内存里。持久化本身正是原型要**检验**的对象，而不是它应当依赖的东西。若问题明确涉及数据库，则使用临时库，或使用命名中带「PROTOTYPE，可随时删除」字样的本地文件。
4. **不做打磨。** 不写测试，除保证可运行之外不做错误处理，不做抽象。目的是尽快学到东西。
5. **暴露状态。** 每次操作之后（逻辑分支），或每次切换变体时（界面分支），输出或渲染完整的相关状态，让用户看清发生了什么变化。
6. **结束时留存。** 把验证通过的决策并入真实代码，然后把原型本身作为**主源**保存：提交到一个从 main 切出的一次性分支，并在实现用的 issue 上留下指向该分支的说明。结论（判定结果及它所解决的问题）也一并记在 issue 或提交里。主分支只保留验证通过的决策。
