用户要做一次**复盘**。你要提出的是针对**编码 agent 运行环境**的改进，目的是让以后的运行更顺。

## 步骤

1. 调用 Skill 工具执行 `x-writing-for-agents`，拿到写作规范。

2. 读用户指定那次会话的一手材料：可能要去翻本机的会话日志。用户没说哪次，就默认当前这次。

3. 在下面这些类别里找改进候选。

- **导航**：agent 找对文件容易吗？文件之间有没有隐藏依赖？加一个**导航指针**会不会更好？_适用时机_：这次会话花了很久才找到某个信息。
- **自动化检查**：有没有哪种自动检查本可以拦住 agent 犯的错？lint、类型检查、测试、文件系统 lint？先读仓库自己的检查命令（`package.json` / 构建工具的 `lint`/`check` 脚本、CI 工作流）——**已在仓库里存在但没接上、或悄悄坏掉的检查，本身就是发现**，不是让你重新造一个。一个**没有任何护栏**（既没有 pre-commit hook，也没有跑 lint/类型/测试的 CI job）的仓库，本身就是发现：没上 lint 的仓库是长期错失的机会，不是中性默认。_适用时机_：agent 犯的错本可以被自动检查拦住，或仓库压根没有护栏。
- **编码规范**：要不要给**评审 agent** 增加一条新规则？要不要删掉或澄清一条旧规则？先给违规分类：**机械型**（固定的语法模式、被禁的 API、import 形状、文件位置规则）就该用确定性检查来兜——仓库自带 linter 的自定义规则、新的 pre-commit hook、新的 CI job，哪个最便宜用哪个。**默认用检查代替规则**。`CODING_STANDARDS.md` 只留给真正的**判断题**（跨文件一致性、"跟周边风格保持一致"这类任何护栏都替代不了的东西）。_适用时机_：评审 agent 没抓出某个错。
- **全局 AGENTS.md**：有没有本该挪进编码规范（或自动化检查）的引导性指令？_适用时机_：AGENTS.md 特别长——仓库内的或用户全局的都算。
- **工具开销**：agent 有没有做出昂贵但可以精简的工具调用？有没有哪个自定义工具（CLI、MCP）特别费 token？_适用时机_：agent 做了一次昂贵的工具调用。
- **无效指令**：引导文件里有没有对 agent 行为毫无影响的条目。_适用时机_：引导文件又多又乱。
- **信息可及性**：有没有办法让 agent 拿到更多信息？把 dev server 日志 tee 出来、给第三方服务只读权限。_适用时机_：某条关键信息 agent 拿不到。

4. 按严重程度排序，把候选改进呈现给用户。

## 参考

### 实现与评审的分工

所有工作都经过两个阶段：实现与评审。**实现型 agent 的上下文压力最大**——探索、写代码、调试失败都归它。

**评审型 agent 的上下文压力最小**——它只拿到一个 diff，不需要探索，通常也不用写代码或调试。

**所以编码规范应该由评审 agent 来施加，而不是实现 agent。**

### 仓库里的几类文件

- `CLAUDE.md` / `AGENTS.md`：会被推入任何在本仓库工作的 agent 的上下文窗口。**要极度克制地使用**，通常只用来放指向其他文件的**导航指针**。
- `CODING_STANDARDS.md`：在评审时读，实现时不读。如果它超过 1000 行，就加**导航指针**指向 docs 目录。
- 文档：当成参考资料用，由其他文件指向它。写新文档之前先找有没有现成的。
- Skills：用来放文档（因为它的 description 会进 agent 上下文），或放用户主动调用的命令。写法遵循 `x-writing-for-agents` 的建议。
