一个粗略的想法到来了，大到一次 agent 会话装不下，而且笼罩在迷雾中：从当前位置到**目的地**的路径还看不见。探路要解决的是找到这条路径，而不是朝目的地猛冲。本技能把路径画成仓库 issue tracker 上的**共享地图**，再逐张处理其中的**决策型 ticket**——这类 ticket 的答案是决策，而不是待执行的实现切片，直到路线清晰。

目的地因事而异，为它命名正是画图的第一步：它决定每张 ticket 的形状。它可能是一份需要交接并反复迭代的 spec，可能是规划开始前必须敲定的某个决策，也可能是就地完成的改动，例如数据结构迁移。地图与领域无关：工程工作、课程内容，只要形状相符都可适用。

## 只做规划，不动手

探路默认只做**规划**：每张 ticket 解决一个决策，地图在路已清晰、动工前再无待决事项时完成。那种「干脆直接动手」的冲动，通常意味着你已经走到地图边缘，该交接了。某项工作可以在其 **Notes** 一节中声明例外，把执行纳入地图内部；但若无此说明，产出决策，而非交付物。

## 以名称相称

每张地图与每张 ticket 都是一个 issue，因此都有**名称**，即其标题。在人类阅读的一切内容中（叙述、地图的「已定决策」），都用名称指代，绝不用裸 id、编号或 slug 代替。满屏的 `#42, #43, #44` 无法阅读；名称一眼可辨。id 与 URL 并未消失：名称本身承载链接，二者藏在名称之内，绝不顶替名称。

## 地图

地图是本仓库 issue tracker 上的一张 issue，标签为 `wayfinder:map`，是这套工作的权威产物。其 ticket 是地图的子 issue。

地图是**索引**，不是仓库。它列出已做出的决策，并指向承载细节的 ticket；每个决策只存在于一处，即它的 ticket，因此地图从不重述决策，只作摘要并给出链接。

**地图、子 issue、阻塞关系与 frontier 查询具体落在何处，取决于 tracker。** issue tracker 应已提供；若未提供，提示用户先运行 `/w-setup-project`（本仓库中为 `w-setup-project`）。查阅 tracker 文档的「Wayfinding operations」一节，了解**本仓库**如何表达这些内容。若未配置任何 tracker，则默认使用本地 Markdown tracker。

### 地图正文

整套地图的低分辨率视图，每会话加载一次。未关闭的 ticket **不**在此列出：它们是未关闭的子 issue，通过查询获得。

```markdown
## Destination

<走完这张地图意味着什么：本次工作要找到的 spec、决策或改动。一两行即可；每次会话选 ticket 之前都要先对照它。>

## Notes

<领域；每次会话都应调用的技能；本次工作的既定偏好>

## Decisions so far

<!-- 索引：每个已关闭 ticket 一行，足够判断相关性，细节点进链接查看 -->

- [<已关闭 ticket 标题>](link): <答案的一句话摘要>

## Not yet specified

<!-- 见「战争迷雾」：范围内但暂时无法开成 ticket 的迷雾；随着 frontier 推进逐块升级为 ticket -->

## Out of scope

<!-- 见「不在范围内」：已被判定超出目的地的工作；关闭，永不升级 -->
```

### ticket

每张 ticket 是地图的**子 issue**，其身份即 tracker 的 issue id。正文即问题，体量以一个 100K token 的 agent 会话为限：

```markdown
## Question

<本 ticket 要解决的那个决策或调查>
```

每张 ticket 带一个 `wayfinder:<type>` 标签，取值为 `research`、`prototype`、`grilling`、`task` 之一（见 [ticket 类型](#ticket-类型)）。`wayfinder:` 标签是地图及其 ticket 唯一携带的标签，绝不使用 `ready-for-agent` 这类分诊标签：它们是决策，不是实现工作。

会话**认领**一张 ticket，就是把它指派给推动地图的开发者，并且要在动工**之前**完成，使并发的会话跳过它。指派本身即认领：未关闭且未指派的 ticket 就是未被认领。

阻塞关系使用 tracker 的**原生**依赖关系。这一点很关键：它让 tracker 自身的界面**直观地**画出 frontier，人类不必打开地图就能看到哪些可做。只有不支持原生阻塞的 tracker 才退回正文约定。当所有阻塞该 ticket 的 ticket 均已关闭，该 ticket 即为**解除阻塞**；**frontier**则是未关闭、已解除阻塞且未被认领的子 issue，也就是已知范围的最外缘。

答案不属于正文，而在解决时记录（见[沿地图推进](#沿地图推进)）。解决 ticket 过程中产生的材料以链接形式记在 issue 上，不要粘贴进去。

## ticket 类型

每张 ticket 要么是 **HITL**（需要人在环中，与能代表自己的人**一起**完成），要么是 **AFK**（由 agent 独立驱动）。HITL ticket 只能通过那场实时交流来解决；agent 绝不代为扮演人的一方（一个自问自答的拷问 agent 已经破坏了这条规则）。

- **Research**（AFK）：阅读文档、第三方 API 或知识库等本地资源，以揭示某个决策所等待的事实。由一个调用 Skill 工具执行「research」的 subagent 解决。当前工作目录之外的知识是必需的时候使用。
- **Prototype**（HITL）：通过做一件成本低、粗糙而具体的产物让人对着反应（提纲、粗略样本、桩代码，或界面／逻辑代码），以提高讨论的具体程度，做法是调用 Skill 工具执行「prototype」。原型以材料形式链接。「该长什么样」「该如何表现」是关键问题时使用。
- **Grilling**（HITL）：对话。默认类型。始终调用 Skill 工具两次，分别执行「grilling」与「domain-modeling」。
- **Task**（HITL 或 AFK）：在做出**决策**之前必须先完成的手工工作。无需决策、无需原型、无需调研，但讨论被它卡住。例如：注册某项服务以判断其 API、开通访问权限、搬迁数据以看清其形状。这是唯一**做事**而非**决策**的类型，它凭解除某个决策的阻塞而获得位置，而非凭交付目的地。agent 能独立完成的就独立完成（AFK），否则给人一份精确的清单（HITL）。工作完成即解决；答案记录做了什么，以及后续 ticket 所依赖的事实（凭据位置、新 URL、行数）。

## 战争迷雾

地图**刻意**不完整：看不见的部分就不要画。当前 ticket 之外是**战争迷雾**（fog of war）：你能察觉即将到来、却因仍依附于未解问题而无法确定的决策与调查。解决一张 ticket 会廓清它前方的迷雾，把此刻已可描述的部分逐一升级为新 ticket，直到通往目的地的路清晰、不再有 ticket 剩余。

地图的 **Not yet specified** 一节用来记录那片模糊的视野：疑似的问题、日后需回看的区域。它是通往目的地、尚未探明的 frontier：其中内容都在范围内，只是还不足以开成 ticket。可粗可细，视视野而定；它同时充当路标，让协作者看出这次工作要往哪走。

**是迷雾还是 ticket？** 判断标准是**现在能否把问题说清楚**，而不是现在能否回答它。

- **开成 ticket**：问题已经足够清晰，即使它被阻塞、暂时无法动手。
- **留在 Not yet specified**：现在还说不那么清楚。不要预先按 ticket 粒度切分迷雾：它比 ticket 更粗，当 frontier 推进到那里时，一块迷雾可能升级为若干 ticket，也可能一张都不需要。

**Not yet specified** 排除三类内容：已确定的（Decisions so far）、已成为 ticket 的、以及不在范围内的（下一节）。

## 不在范围内

迷雾只朝目的地聚集。目的地划定范围，超出它的工作即**不在范围内**：它不是迷雾，也不属于 **Not yet specified**，而是地图上单独的 **Out of scope** 一节，记录你已有意排除在**本次**工作之外的部分。判定其归属的是范围，而非清晰度。

不在范围内的工作永不升级（frontier 止于目的地），因此只有在目的地被重新划定后才可能回来，且届时作为一项新工作，而不是接着做。

判定某项工作不在范围内是一种划定范围的动作，不是路线上的一个步骤。当一张既有的 ticket 被发现实际位于目的地之外（画图时误纳，或在解决某张 ticket 时被发现），**关闭它**（已关闭的 ticket 明确地不在 frontier 上），并在 **Out of scope** 一节留下一行：摘要与排除理由，链接该已关闭 ticket。它不进 **Decisions so far**，因为那一节记录实际走过的路线，而范围边界不是路线上的步骤。

## 调用方式

两种模式。无论哪种，**每次会话最多解决一张 ticket**，research 类 ticket 除外。

### 画地图

用户带着一个粗略想法调用。

1. **为目的地命名。** 调用 Skill 工具两次，分别执行「grilling」与「domain-modeling」，确定这张地图要通向什么：spec、决策，还是改动。目的地划定范围，因此要先定下来。
2. **勘察 frontier。** 再次拷问，这次**广度优先**：在整个空间上铺开，而非在任何一条线索上深入，把待决事项与当下可做的第一步摆出来。**若这一步没有发现迷雾**（通往目的地的路已经清晰，整段旅程一次会话即可完成），就不需要地图。停下，询问用户打算怎么办。
3. **创建地图**（标签 `wayfinder:map`）：填写 Destination 与 Notes，Decisions so far 留空，迷雾草绘进 **Not yet specified**。
4. **立即创建此刻能确定的 ticket**，作为地图的子 issue，随后在**第二遍**中接好阻塞边（要先有 id 才能互相引用）。交叉引用也放在这一遍写，且使用真实 id：占位的 `#<n>` 会自动链接到无关 issue。接好边之后，ticket 便分成 frontier 与被阻塞两类；此刻仍无法确定的留在迷雾中，即 **Not yet specified** 一节。
5. **派出调研 subagent。** 对刚创建的每张 `research` ticket，起一个全新上下文的 subagent，调用 Skill 工具执行「research」并行解决，把结论记在一个一次性的 `research/<name>` 分支上，并在 ticket 里留一条指向该分支的上下文指针。分支可以推送，但不要开 PR：它永远不会被合并。
6. 到此为止：画地图本身就是一次会话的工作，它不亲手解决任何一张 ticket。

### 沿地图推进

用户带着一张地图调用（URL 或编号）。ticket 是**可选的**：未指定时，由你而非用户挑选下一个决策。

1. 加载**地图**：低分辨率视图，而不是每张 ticket 的正文。
2. 选择 ticket。用户点名则用其指定的；否则按顺序取第一张 frontier ticket。**认领它**：动工之前先指派给自己。
3. 按其 `wayfinder:<type>` 标签所指的类型解决（见 [ticket 类型](#ticket-类型)）。读标签，不要只看正文：正文从不标明类型。**按需放大**：随时取回相关或已关闭 ticket 的完整正文；调用 `## Notes` 中列出的那些技能。拿不准时，调用 Skill 工具两次，分别执行「grilling」与「domain-modeling」。
4. 记录解决结果：把答案作为**解决评论**发布，**关闭**该 issue，并在地图的 Decisions so far 中**追加一条上下文指针**。
5. 补充新暴露出来的 ticket（先创建，再接边）；把答案已使其可描述的那部分迷雾升级为 ticket，并从 **Not yet specified** 中清除，使其只以新 ticket 的形式存在。若答案表明某张 ticket（本次这张或另一张）位于目的地之外，**判定其不在范围内**，而不是让它留在路线上被解决。若该决策使地图的其他部分失效，更新或删除相应 ticket。

用户可能并行推进多张已解除阻塞的 ticket，因此应预期其他会话正在同时编辑 tracker。
