这个技能拿当前的对话上下文和对代码库的理解，产出一份 spec。**不要访谈用户**，只综合你已知的内容。

issue tracker 与分诊标签词表应当已经提供给你；如果没有，让用户先跑 `/w-setup-project`。

## 流程

1. 如果你还没做过，先探索仓库、了解代码库现状。整份 spec 都用项目术语表里的词汇，并遵守你正触及区域的 ADR。

2. 勾出你打算在哪些 seam 上测这个功能。优先用已有 seam，而不是新建；能用最高的 seam 就用最高的。需要新 seam 时，在尽可能高的位置提议。整个代码库的 seam 越少越好——理想数量是 1。

和用户确认这些 seam 符合他们的预期。

3. 用下面模板写 spec，然后发布到项目的 issue tracker。打上 `ready-for-agent` 分诊标签——不需要再走分诊。

<spec-template>

## 问题陈述

从用户视角看，用户正面对的问题是什么。

## 解决方案

从用户视角看，这个问题怎么解。

## 用户故事

一份**很长的**、编号的用户故事清单。每条格式为：

1. 作为一个 <角色>，我想要 <功能>，以便 <收益>

<user-story-example>
1. 作为一个手机银行客户，我想在账户上看到余额，以便更好地决定怎么花钱
</user-story-example>

这份清单要尽可能详尽，覆盖该功能的各个方面。

## 实现决策

列出已经做出的实现决策，可以包括：

- 要新建/修改的模块
- 这些模块中会被改动的接口
- 开发过程中的技术澄清
- 架构决策
- schema 变更
- API 契约
- 具体的交互

**不要**写具体文件路径或代码片段，它们很快就过时。

例外：如果原型产出的某个片段比文字更精确地表达了决策（状态机、reducer、schema、类型形状），就把它内联进对应的决策里，并简短注明来自原型。只留承载决策的关键片段，不要贴一个能跑的 demo。

## 测试决策

列出已经做出的测试决策，包括：

- 说明什么算好测试（只测外部行为，不测实现细节）
- 哪些模块会被测
- 测试的先例（代码库里类似的测试类型）

## 不在范围内

说明这份 spec 不覆盖哪些东西。

## 补充说明

关于该功能的其他说明。

</spec-template>
