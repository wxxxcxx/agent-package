# 拆分工单

把计划、spec 或对话拆成一组**工单（工单）**。每张工单只打通一条窄而完整的路径，贯通 schema、API、UI 与测试各层，做完即可独立验证；同时声明它**依赖**哪些工单先完成。

issue tracker 与分诊标签词表应已提供；若未提供，提示用户先运行 `/w-setup-project`。

## 流程

### 1. 收集上下文

以对话上下文中已有的材料为起点。若用户在参数中传入引用（spec 路径、issue 编号或 URL），取回并通读其正文与评论。

### 2. 探索代码库（可选）

若尚未探索代码库，先完成探索以了解代码现状。工单标题与描述应使用项目的领域术语表词汇，并遵守所涉区域的 ADR。

留意可先行重构之处，使后续实现更简单。「先让改动变容易，再做容易的改动。」

### 3. 划分工单

将工作拆为若干张工单，每张都是一条端到端的最小闭环。

<vertical-slice-rules>

- 每张工单贯通各层（schema、API、UI、测试），形成一条窄而**完整**的路径；沿纵向推进，不做只改一层的横向铺开
- 单个切片完成后可独立演示或验证
- 每个切片的体量应能装进一个全新的上下文窗口
- 先行重构应排在最前

</vertical-slice-rules>

为每张工单标注**阻塞边**：即必须先完成的其余工单。没有阻塞的工单可立即开始。

**大范围重构是上述做法的例外。** 所谓**大范围重构**，指一次机械改动（重命名列、变更共享符号的类型），其**波及面**横贯整个代码库，单次编辑会同时破坏成千上万个调用点，任何单张工单都无法单独保持绿灯。此时不要硬压成一张垂直切片的工单，而应按**扩张—收缩**排序。先扩张：在旧形式旁加入新形式，使任何部分都不致损坏。再迁移：按波及面分批迁移调用点（按包、按目录），每批各自成为一张工单，阻塞于扩张工单；由于旧形式仍在，批次之间可保持 CI 绿灯。最后收缩：确认无调用者后删除旧形式，该工单阻塞于全部迁移批次。若连分批也无法单独保持绿灯，则保留上述顺序，但让各批共享一个集成分支，并让全部批次共同阻塞一张最终的集成验证工单；绿灯只在这张工单处承诺。

### 4. 与用户确认

以编号列表呈现拆分方案。每张工单给出：

- **标题**：简短描述性名称
- **阻塞于**：须先完成的其余工单（若有）
- **交付内容**：该工单打通后的端到端行为

向用户确认：

- 粒度是否合适（过粗／过细）
- 阻塞边是否正确：每张工单是否只依赖真正卡住它的工单
- 是否有工单需要合并或进一步拆分

反复调整直至用户认可。

### 5. 发布到已配置的 tracker

发布已确认的工单。**发布方式**取决于 `/w-setup-project` 配置的 tracker；工单内容一致，仅阻塞边的形式不同：

- **本地文件**：在 `.scratch/<feature-slug>/issues/<NN>-<slug>.md` 下每张工单一个文件，按依赖顺序从 `01` 编号（阻塞方在前）。每个文件的「Blocked by」列出其所依赖的编号与标题。使用下方单张工单模板：一张一个文件，绝不合并为单一文件。
- **真实 issue tracker（GitHub、Linear 等）**：按依赖顺序、阻塞方在前，每张工单发布为一个 issue，使阻塞边可引用真实标识符。平台支持原生阻塞关系时使用之；否则将每张工单的「Blocked by」设为阻塞它的 issue。若来源是一份既有 issue，则让每张工单成为它的子 issue（按 tracker 文档中的操作）。除另有说明，一律打上 `ready-for-agent` 分诊标签：这些工单按构造即可被 agent 领取。

始终处理**前沿**：所有阻塞均已完成的工单。纯线性链条即从上到下。

不得关闭或修改任何父级 issue。
